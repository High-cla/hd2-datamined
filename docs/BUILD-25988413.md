Definitive record of the 10-20 update, written from measurements taken on this machine. Everything here
was read from bytes on disk or from output the game itself produced; nothing is inferred from community
posts alone, and where a claim IS community-sourced it says so.

## 2. The Lua VM changed: LuaJIT → stock Lua 5.1.4

Every `lua` resource in the old build is a **LuaJIT** chunk (`1b 4c 4a 02` = `\x1bLJ`); every one in the
new build is a **stock Lua 5.1** chunk (`1b 4c 75 61 51 00 01 04 04 04 08` = `\x1bLua` + 0x51 + standard
type sizes). Confirmed at runtime by the in-game probe, both directions:

```
LuaJIT chunk (22 B):        load REFUSED -> binary string: bad header in precompiled chunk
stock Lua 5.1 chunk (175 B): load ok, run ok=true
VERDICT: this VM runs stock Lua 5.1 chunks only
```

and by the environment itself:

```
_VERSION = Lua 5.1        type(jit) = nil   type(ffi) = nil   type(bit) = nil
```

`bin/helldivers2.exe` contains the literal `Lua 5.1.4` in its plaintext `.rdata`, and no `LuaJIT`,
`jit.opt` or `ffi.*` strings anywhere readable.

**Consequence:** `ffi` is gone. Every technique in this project that touched process memory through
LuaJIT's FFI - component-table reads, RVA-anchored scans, the whole `mount_recon` / `memscan` /
`HD2Runtime` family - has lost its entry point. This is not a re-derivation problem; there is no route.

## 4. What broke, per class of mod

| class | state | why |
|---|---|---|
| **Lua mods** (any logic) | **dead** | the only in-process lua entry (`core/wwise/lua/wwise_flow_callbacks`) was deleted from the game, and `boot` no longer `require`s it; additionally the old loader payload is LuaJIT bytecode, which this VM cannot load at all |
| **Memory mods** (`ffi` + RVA) | **impossible** | no `ffi`; no documented memory API in `_G` |
| **Asset mods** (mesh/material/texture/particle/audio) | **likely fine, under verification** | they are `.patch_N` resource overrides, and the patch mechanism is proven alive (§5). Caveat: `unit` resources are known to desync from game data after updates (community tool `hd2-repatcher` exists for exactly that) |
| **Patch mechanism itself** | **alive** | see §5 |

Important: **an asset-only mod needs no loader.** The loader exists to execute lua logic. A cosmetic mod
is just a patch archive that replaces resource ids, and patch archives still override base resources.

## 5. The patch mechanism is alive — proven in game

A probe patch installed as `data/9ba626afa44a3aa3.patch_0`, containing exactly one resource -
**`boot` (id `0xF476DF93691895FA`)** with a plain Lua **source** payload - ran in-game:

```
===== BootProbe 1.1.0 | build 25988413 | 2026-10-20 17:47:28 =====
REACHED: this line can only exist if a .patch_N overrode the base `boot` resource
```

Two separate facts follow, and both were in doubt:
1. `.patch_N` archives still override base-game resources.
2. The engine accepts a **source** payload where the shipped resource is bytecode.

The probe's body reproduces the game's own `boot` verbatim (four no-op entry points, the
`build ~= "release"` debug guard, `jit.off()` when `jit` exists) before doing anything else, so a
failure inside the probe cannot change engine startup behaviour. It ran, the game booted normally, and
the log was written - no crash.

### The anchor, as a recipe

- resource: `boot`, id = `murmur64("boot")` = `0xF476DF93691895FA`, lives in bundle `9ba626afa44a3aa3`
- patch file: `data/9ba626afa44a3aa3.patch_N` (+ empty `.gpu_resources` and `.stream` companions)
- payload: `u32 size | u32 2 | <lua source>` (srkit's lua envelope), source is fine, bytecode optional
- must assign globals `init`, `shutdown`, `update`, `render` - that is how the engine reads the entry script
- `boot` is the **only** lua the engine loads by itself: the new build ships 9 distinct lua resources and
  `core/init` exists in neither build, so there is no alternative anchor

## 9. Answered: asset overrides still work (2026-10-20 18:22)

The open question in §7 was "do asset mods actually still load?". It is answered, in game, with the
combined patch (`boot` lua + **6 mesh overrides** of real base unit ids taken from ArmoredOverhaul's

So the engine accepts mod-supplied **non-lua** resources through the same `.patch_N` mechanism, on this

generation are unchanged, this means:

- **cosmetic / non-gameplay asset mods are viable right now** - they never needed the shared loader;
- the "everything is dead" reading of this update was wrong for the asset class, and only true for

## 10. Loader feasibility proven: `boot` can start a mod that lives in another patch

The last open question was whether a boot-anchored loader can actually start other mods. It can. Measured
in game on 2026-10-20 19:51:53 with two patches deployed and nothing else:

- `patch_0` = `boot` override only (a "mini loader", 21,008 B)
- `patch_1` = a read-only test mod (3,824 B), module path `mods/test/boot_loader_test`,
  resource id derived as `murmur64(module)` = `0x0D90A720EBC2F7D3C`… (`d90a720ebc2f7d3c`)

The boot payload ran the engine's own recipe, copied from the old loader's source
(`assert application.can_get('lua', name)` then `require(name)`, and never let a missing resource reach
require):

```
Application.can_get = function
make_hash('mods/test/boot_loader_test') ok=true -> d90a720ebc2f7d3c     <- equals our derived id
control can_get('lua', absent):                    ok=true value=false   <- the probe discriminates
can_get('lua', 'mods/test/boot_loader_test'):      ok=true value=true
require('mods/test/boot_loader_test'):             ok=true type=table value=table: 00000291D21FEB80
require took 0.001 s
RESULT: SUCCESS - a boot-anchored loader started a mod that lives in another patch
```

and the test mod's own log proves it executed, not merely loaded:

```
TEST MOD EXECUTED: this line can only exist if another patch's lua resource was required and run
module = mods/test/boot_loader_test
... (what require passed) = mods/test/boot_loader_test
_VERSION = Lua 5.1
BootLoaderTestShared.loaded = 1
```

What this settles:

1. **Patches are per-bundle, not per-file.** A resource from `patch_1` is visible to code running from
   `patch_0`. A loader does not have to be bundled with the mods it starts.
2. **`Application.can_get('lua', name)` works on this build** and answers false for an absent module and
   true for an installed one - so "does this mod exist?" has an API, without `ffi`.
3. **A module's resource id is exactly `murmur64(module path)`**, confirmed twice: by our own derivation
   and by the engine's `make_hash` agreeing in game. A loader can compute any mod's id from its path.
4. `require` passes the module path through as a vararg and returns the mod's return value, so ordinary
   mod code loads unchanged - no API change is needed on the mod side.

**Correction to an earlier claim of mine.** `LOADER-SPEC` said there was no discovery primitive left.
`Application.can_get` is one, it was in the 70 keys we had already enumerated, and the old loader had been
using it all along. What genuinely died is *filesystem* enumeration (`ffi` + `FindFirstFile`), not existence
checking. With `make_hash` + `can_get` + `require`, a loader that is given a naming convention can probe a
candidate list entirely in engine terms; only "which names to try" remains open, and that is a
deployment/manifest question, not an engine one.

## 11. Answered: memory access is gone on both sides (2026-10-20 20:39, live pid 6552)

Full record: [`MEMORY-ACCESS-25988413.md`](MEMORY-ACCESS-25988413.md).

- **Inside the process**: `ffi` is nil, so `memscan` / `memmod` / any raw read is dead. `memscan`'s
  payload dies at its own line 11, `module 'ffi' not found`. Of its 41 ffi lines only **13 are the OS
  binding**; the rest is pure byte arithmetic over a string, so the tool is repairable *in shape* but
  has no byte source left.
- **Outside the process**: EAC grants the handle and **strips `PROCESS_VM_READ`**. Measured on a
  committed MEM_IMAGE region: `ReadProcessMemory` → `err=5`; `MiniDumpWriteDump(MiniDumpNormal)` →
  `0x80070005 E_ACCESSDENIED`, 0 B file. The old `crash_watch.py` → `dumper.ps1` pipeline is dead.
- **What still answers questions**: `VirtualQueryEx` + `GetMappedFileNameW` need only
  `QUERY_INFORMATION`, so the whole module map is still readable without touching a byte:
  `game.dll` `0x1ced0440000` (51.51 MB, one contiguous region), `helldivers2.exe` `0x1ceb8520000`
  (41.99 MB, one region), `runtime.dll` `0x00ffab0000` (123.88 MB, 28 regions); 11,150 MB committed
  overall. Saved as [`recon/addrspace-25988413.tsv`](../recon/addrspace-25988413.tsv).
- **My own error, recorded**: the first `eac_access_test.py` judged by `OpenProcess` alone, saw three
  GRANTED, and printed a READABLE verdict. That was a false positive - EAC does not refuse the handle,
  it weakens it. The tool now reads eight bytes from a committed image region, and its selftest
  replicates the stripped-handle shape with a deliberate `0x0400`-only handle (5 PASS / 0 FAIL).
