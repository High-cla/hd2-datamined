# 纯 Lua 屏幕 HUD 线（build 25988413）

> 目的：运行期读的五条路全关了，但「Lua 逻辑」这一半还活着。这条线在回答一个问题 ——
> **不用 ffi、不写内存，纯 Lua 能不能自己画屏幕文字？**
> 如果能，计时器 / 状态提示 / 自己算出来的数值显示这一类 mod 就全通，而且是 EAC 策略下最干净的一块。

本文件只记**已实测**的东西；推断标 ⚠，否证标 ✗。

## 1. 三次崩溃教出来的东西

| 版本 | 走到哪 | 崩在 | 根因 |
|---|---|---|---|
| 0.1.0 | `create_screen_gui` → `set_visible` → `is_visible` 全通 | `Gui.text(gui, "…")` | 只给了 2 个参数；真实签名要 6–8 个 |
| 0.2.0 | 同上 + `Gui.get_id` 报 nil（安全） | `Gui.resolution(gui)` | **`resolution` 不是 self 方法**：签名是 `resolution(viewport, window)`，把 Gui 当 Viewport 传 = 原生 AV，`pcall` 拦不住 |
| 0.3.0 | 见 §3 | — | — |

两条纪律是从这两次崩溃里换来的：

1. **参数形状不能猜。** 猜错的代价是整个进程，一个数据点换一次游戏启动。
2. **文档只能用来排序，存在性必须以实测键表为准。** `Gui.get_id` 在官方文档里有、在本 build 里
   **不存在**（routes 1.1.0 实测 `Gui.__index` 只有 46 键）。反过来 `resolution` 存在但签名完全不是
   self 方法 —— 只看键名不看签名，等于没有信息。

## 7. 定案（2026-10-21 19:53，0.5.0 实机 A/B）

同一次启动里**两种模式同时建**，屏幕上直接分出胜负 —— 截屏 + 日志双证：

| 模式 | 构造 | 代码侧回报 | 屏幕 |
|---|---|---|---|
| **retained** | `World.create_screen_gui(world, "scale", 1, 1)`，画一次存 id | id=0、id=1；`is_visible=true` | ✓ **`DSH RETAINED` + `DSH LINE2` 两行都在** |
| immediate | `World.create_screen_gui(world, "immediate")`，每帧重画 | `is_visible=true`，`imm_draws` 计到 3600 | ✗ **一个字都没有** |

日志原文（`ExpHud.log` 0.5.0 段）：

```
STEP A5 Gui.text(gui_ret, 'DSH RETAINED', font, 48, mat, Vector2(120,300), Color)
   pcall_ok=true  n=1  ret#2=number:0            <- retained 返回 id
STEP A6 Gui.set_visible(gui_ret, id, true)   [per-primitive]
   pcall_ok=true
RESULT: YES - retained gui=true immediate gui=true
C1 frame=21600 imm_draws=3600  visible(retained)=true  visible(immediate)=true
```

⇒ **`is_visible` 不是判据**（两种模式都返回 true）；判据只有**屏幕上有没有**。
⇒ 这个 build 的 immediate 模式**调用全部成功但不被合成器绘制** —— 这是 0.1.0/0.3.0 一直"看不见"的真因，
   不是字体、不是材质、不是坐标、不是 world 没渲染。

## 8. 0.9.0：把"性能 + 网络"读数做出来（2026-10-21 21:2x）

### 8.1 三条数据的来路

| 指标 | 接口 | 单位/口径 |
|---|---|---|
| 帧率 / 帧时间 | **`update(dt)` 的参数**（EMA 平滑 + 900 帧滚动 min/avg/max）| 秒 → ms |
| 进程运行时长 | `Application.time_since_launch()` | 秒（官方文档确认）|
| P2P 延迟 | `Network.ping(peer_id)` | ★**秒**，×1000 才是 ms |

`Network.ping` 的配方取自社区 **P2P-Ping 0.1.34**（`D:\Downloads\P2P-Ping-...zip` 里的
`mods/shock233/p2p_ping`，636 行）。它需要的那批函数在本 build 的运行时 dump 里**全部存在**：

```
Network.ping / peer_id / game_session            ✓
GameSession.in_session / peers / game_session_host ✓（33 个成员里都有）
```

它是这个形状：

```lua
local session = Network.game_session()
if GameSession.in_session(session) ~= true then return end
local peers = GameSession.peers(session)          -- peer id 数组
local mine  = Network.peer_id()
for i = 1, #peers do
    if tostring(peers[i]) ~= tostring(mine) then
        local seconds = Network.ping(tostring(peers[i]))   -- ★秒
        local ms = (seconds > 0 and seconds < 60) and math.floor(seconds * 1000 + 0.5) or nil
    end
end
```

采样 **2 秒一次**（真的发一次往返，不能每帧）。颜色阈值沿用它的：≤90 ms 绿 / ≤180 黄 / 否则红。

### 8.2 两个安全要点

1. `GameSession.peers()` 返回的是 **peer id（字符串）**，不是引擎句柄 —— 遍历它是安全的，
   和 `World.units()` 快照完全两回事（后者句柄会失效，见 STINGRAY-API 的事故记录）。
2. 全程 `callable()` 先探存在、`attempt()`(=pcall) 包住，任何一步拿不到就**停下并写清原因**。
   这不是我们发明的写法 —— 社区 P2P-Ping 通篇如此，说明这些 API 在老 build 上也咬过人。

## 9. rtt_hud 1.0.0：只显示 P2P 延迟（P1–P4 + HOST）

`exp_hud.lua`（全指标版）保留在仓库里；这一版是专门的延迟面板，装成 patch_1。

### 9.1 目标选择规则（这是 P2P 的关键）

抄社区 P2P-Ping 的策略 —— 它恰好覆盖了"只当 host 测过"这个盲区：

| 我是谁 | ping 谁 |
|---|---|
| **host** | 所有远端 peer |
| **client**（host 已知且不是我）| **只有 host** —— P2P 里客户端之间通常没有直连 |
| host 未知 | 退回 ping 所有远端 |

### 9.2 槽位映射（编号稳定，但初始顺序有已知不确定性）

沿用社区做法：
- **首次**：按 `GameSession.peers()` 的数组顺序发 P1..P4，并在日志里记
  `initial_array_order_is_unverified=true` —— 数组顺序**未必等于**游戏内小队槽位顺序
- **之后**：peer 消失就释放槽位（记 `peer_slot_released Pn`），新 peer 拿最小空槽
  （记 `peer_slot_assigned Pn`）⇒ 编号不会因为有人进出而整体跳变

### 9.3 屏幕

```
P2P RTT   you: P1 (ping all)      ← host 时加 (ping all)；client 只显示 you: Pn
P2  42 ms                         ← 绿 ≤90
P3 HOST  129 ms                   ← 黄 ≤180，红 >180
```

不在局内时只显示一行 `-- not in session --` / `-- no remote peers --` / `-- api missing --`。

### 9.4 离线排练（client 分支）

把假引擎改成"我是 me、host 是 peer-alpha、peers={me,peer-alpha}"，排练 300 帧：

```
slot_tracker_initialized peers=2 initial_array_order_is_unverified=true
rtt P2 HOST=42ms | targets=1 host_detected=true local_is_host=false
```

⇒ ✓ client 分支走通：识别出 host、目标只锁 host、标签带 HOST。

### 9.5 实机：host 与 client **同一次启动内都验到了**（✓ 2026-10-21 21:33–21:36）

`ExpHud.log` 只有一个 `rtt_hud 1.0.0` 段，里面完整记录了一次 **host → client 的切换**：

```
rtt P2=134ms            ... local_is_host=true        ← 我是 host，ping 所有远端
peer_slot_released P2                                  ← P2 离开
rtt no remote peers     ... local_is_host=true
rtt not in session      ... local_is_host=true         ← 掉出局
peer_slot_assigned P2                                  ← 新局里同一个槽位被重新分配
rtt P2 HOST=123ms       ... local_is_host=false        ← 我成了 client，目标自动锁到 host
```

⇒ ✓ **目标选择规则与 HOST 标签都是活的**：同一进程内角色一变，ping 目标和标签立刻跟着变，
不需要重载模块。
⇒ ✓ 截图与日志互相印证：`you: P1`（无 `(ping all)`）+ 单行 `P2 HOST 125 ms`。

### 9.6 ★ 发现一个真问题：刚进局时 ping 会短暂返回 ~0

同一次切换之后，前几拍读数是这样爬上去的：

```
P2 HOST = 0ms → 35ms → 54ms → 89ms → 108ms → 稳定 ~120–130ms
```

`0ms` 不是真实往返（我们的门槛是 `seconds > 0`，所以它真的是一个极小的正数，
×1000 取整后变 0）。这是一次**会话重建后的测量预热**，社区 mod 也有同样的现象
（它的门槛与我们相同，所以它也会显示 0）。

⇒ **下一版要做的**：会话或 peer 集合一变（`in_session` 翻转、或 `peer_slot_assigned`），
**丢弃前 3 拍样本**并标成 `warming up`，别让 0 ms 闪一下骗人。

### 9.7 rtt_hud 1.1.0：预热过滤 + min/avg

针对 §9.6 那个"刚进局闪 0ms"的问题：

| 机制 | 行为 |
|---|---|
| **预热过滤** | 每个 peer 的**前 3 拍读数丢弃**，屏幕显示 `warm-up 1/3`，日志记 `warm1/3` |
| **状态清理** | peer 消失即删它的预热计数与历史（`peer_slot_released` 那条路径）；`in_session` 变 false 时清空全部（日志记 `warm-reset (left session)`）⇒ 换局必然重新预热 |
| **min/avg** | 保留最近 10 个有效样本，同时显示 `min` 与 `avg`，一眼看出抖动 |
| **读不到** | 保留 `n/a`，且**不计入**预热次数（避免网络抖动把预热计数吃掉）|

屏幕单行示例：

```
P2 HOST  warm-up 2/3
P2 HOST  124 ms   min 118  avg 126
```

离线排练（800 帧 ≈ 6.7 秒，覆盖 3 拍预热）：`warm1/3` → `42ms(min42/avg42)` 两处期望全中。

### 9.8 rtt_hud 1.2.0：加 max，收紧排版

| 项 | 1.1.0 | 1.2.0 |
|---|---|---|
| 统计量 | min / avg | **min / avg / max**（同一窗口最近 10 个有效样本）|
| 行距 | 64 px | **48 px** |
| 字号 | 标题 40 / 行 34 | **标题 34 / 行 28** |
| 左边距 | 60 px | **40 px** |
| 对齐 | `%-8s` + 变宽数字 | **标签 `%-9s`、数字定宽 `%4d`** ⇒ 多行数字上下对齐 |

排版目标：一屏能整块读完，且**数字列对齐**（不然 66 与 172 宽度不同会显得散）。

```
P2P RTT  you: HOST (ping all)
P2 HOST  172 ms   min  172  avg  182  max  196
P3       167 ms   min  167  avg  180  max  191
P4        66 ms   min   66  avg   71  max   78
```

`max` 的价值：`min` 与 `avg` 接近但 `max` 高出一截 ⇒ 有卡顿/尖峰；三者都稳 ⇒ 链路平稳。

离线排练：`warm1/3` → `42ms(min42/avg42/max42)`，2/2 命中，无 raise。

### 9.9 1.2.0 验收通过（✓ 2026-10-21 21:5x，3 人局）

```

rtt P2=warm2/3 | ...
