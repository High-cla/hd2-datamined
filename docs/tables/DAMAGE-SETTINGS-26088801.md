## 1. 文件与容器

### 1.1 文件身份

| 项 | 值 |
|---|---|
| 明文 | **50,336 B** |
| 封包 | **50,384 B**（= 明文 + 48，密封盒固定开销） |
| 明文 `Murmur64A` 锚点 | **`D03587CCBD2FECFC`** |
| 原版封包 sha256（前 16 位） | `f425756e3d9ff4f0` |
| 本轮产物封包 sha256（前 16 位） | `4e01585ec964c58e`（tail 版）；行宿主中间版 `2217925620537a04` / `ad882a4b68e74865` |
| 容器范围 | `0x4 → 0xC4A0`（= 50,336），两块首尾相接，**没有尾部残留** |

这是仓库第 **5** 张留档明文锚点的表（前四张：战备 / 爆炸 / 弹丸 / 实体库）。它同时是第 1 张
**行内零 padding 却被打开改写**的表 —— 结构上「没空隙」，不等于整份文件「没宿主」（§5）。

### 1.2 两个 `LDLD` 块

| 块 | 绝对偏移 | `type_id` | 元素 / stride | 内容 | payload |
|---|---|---|---:|---|---:|
| 0 | `0x4` | `0xEB1433DA` | — / 32 | `DamageArmorAngles`：**单条 32 B 记录，无 count 头**；字段 = `Projectile[4]f32` + `DPS[4]f32`（本文实测 `25/60/80/90` 两组，见 §9.5）| 32 |
| 1 | `0x3C` | `0xE0A72CF0` | `DamageInfo` / **76** | `DamageSettings`：头 `(marker=16, count=661)`，行区绝对起点 `0x64` | 50,252 |

- **块 0 没有数组描述符**：8 个 f32 直接从 `0x1C` 开始 —— `25, 60, 80, 90, 25, 60, 80, 90`。
  fileDiver 把这两组四个叫 `Projectile[4]` 与 `DPS[4]`（⚠ 未与本 build 的值对照）。
- **块 1 的 payload 一分不剩**：16 B 描述符（`u64 相对偏移 0x10`、`u32 count = 661`、`u32 pad = 0`）
  + `661 × 76 = 50,236`，合计 `50,252` = payload 大小。⇒ 想走 tail 必须同时改末组 `payload_size`（§5.3）。
- 两个组头的 `wide` 字节都是 `1`（64 位布局），`+16` 那 7 字节保留区全 0。**但** `+16` 字的绝对偏移是
  `0x14` / `0x4C`，都 ≡ 4 (mod 8) ⇒ 常见的「组头宿主」在本表**对齐不满足**（§5.2）。
- 描述符的 `pad` 落在 `0x60`（8 字节对齐），可它只有 4 字节：紧接着 `0x64` 就是第 0 行的 `+0` 主键（值 `1`）
  ⇒ 凑不出一个完整的 8 字节字（§5.2）。

## 2. 字段图 `DamageInfo`（76 B）

| 偏移 | size | typelib 类型 | 候选成员名（fileDiver） | 实测 | 三态 |
|---|---:|---|---|---|---|

| `+8` | — | — | `DurableDamage`（int32） | 耐久伤害，分布同上 | **✓ 离线（语义 ⚠）** |
| `+12` | 16（4×u32） | primitive | **`ap_direct` / `ap_slight` / `ap_large` / `ap_extreme`** | 4 个角度穿甲等级，各 0..20 | **✓ 外部双源**（§9） |
| `+28` | 4 | primitive | **`Demolition force`**（拆解力） | 0..80（`10` → 249 行、`30` → 146 行） | **✓ 外部双源 / ⚠ 无改动实验**（§9） |
| `+32` | 4 | primitive | **`Stagger force`**（硬直力） | 0..600 | **✓ 外部双源 / ⚠ 无改动实验**（§9） |

| `+40` | 4 | enum `0x86B0A9AC` | **`ElementType`（元素类型）** | 枚举 0..9，548/661 是 0；0–5 的语义由「`+44` 状态槽交叉表」独立印证（§9.4） | **✓ 外部 + ✓ 离线交叉印证**；6–9 ⚠ |
| `+44` | 32 | 数组 4 × 8 B，元素 `{enum 0x525E8B93 @+0, u32 @+4}` | **`StatusEffects[4]` = 4 × {`StatusEffectType`, `strength`}** | 状态槽：type 指向 `status_effect_settings` 的行，**那行的 `+44` 又指回一条伤害行**（持续伤害）；只有前 1–2 个常用，第 4 对全表 0 | **✓ 外部双源**（§9） |

**零 padding 的算术**：`4 + 8 + 16 + 4 + 4 + 4 + 4 + 32 = 76`。8 个成员把 76 B 铺满，
**行内一字节空隙都没有** —— 这正是当年判定「伤害改不了」的直接依据（§5.1 说明它错在哪）。

几条容易混淆的细节：

- typelib 说「8 个成员」与本文说「9 个语义字段」**不矛盾**：`+4` 那个 8 B primitive 成员装的是两个
  `int32`（`+4` 标准伤害 / `+8` 耐久伤害），`+12` 那个 16 B 成员装的是四个 `u32`。
- `+4` 的 `-1` 哨兵只有 3 行：id **279 / 281 / 490**（`+8` 也同时是 `-1`）。值域上界 10000：
  id **277 / 491 / 509 / 661**。
- 状态槽非空行数：槽 0 = **157**、槽 1 = **29**、槽 2 = **5**、槽 3 = **0**。有 **29 行**带 ≥2 个状态效果。
- fileDiver 的解析器遇到第一个 `type == 0` 就 `break`（`StatusEffects` 是**前缀有效**）。⚠ 这是
  **外部解析器**的行为，不代表引擎也这样读 —— 但它解释了「为什么第 4 对永远是 0」。
- `+12..+24` 与 `+28/+32/+36` 现由**两个互相独立的外部来源**（一个社区编辑器、一个基于 HD2Runtime 的 mod）
  在名称与偏移上完全一致（§9），所以「叫什么」已经从 ⚠ 升到 ✓。
  **但「改了会怎样」仍无本方实验** —— 尤其 `+28/+32/+36` 是力的量级，改动的可观察量与伤害不同，配方见 §8.3。
- `+40` 两个来源都没有名字，保持 ⚠。

## 3. 引用关系：谁指向这张表

`DamageInfoType` 在类型库里是 **enum `0x39D2F78D`**。把 54 张标准表**每个组的元素类型**都按 typelib 扫一遍，
只保留「`size == 4` 且 `type_id == 0x39D2F78D`」的成员 —— 全库只有下面 **5 个字段**命中
（`generated_entities` 是块序列，不在这次扫描内，见 §8.6）。

### 3.1 完备扫描（5 张表）

| 来源表 | 字段 | 行数 | 命中 `1..661` | distinct id |
|---|---|---:|---:|---:|
| `generated_projectile_settings` | `+60` | 355 | 349 | **238**（含 `0` 共 239） |
| `generated_explosion_settings` | `+4` | 424 | 406 | **238**（含 `0` 共 239） |
| `generated_arc_settings` | `+36` | 16 | 16 | 14 |

### 3.2 并集与「无主池」：两个口径

| 口径 | 引用 id（非零） | 无主行 | 其中 4 槽全空 | 其中 8 字节对齐可用 |
|---|---:|---:|---:|---:|
| 两表（弹丸 + 爆炸） | 474 | **187** | 122 | 87 |
| **五表（+ arc / beam / status_effect）** | **530** | **131** | **97** | **60** |

- 算式：`661 − 474 = 187`；`661 − 530 = 131`。
- **两表口径就是 `tools/dmg_refs.py` 的输出**（它只认弹丸与爆炸）：`orphan rows (no projectile/explosion reference): 187`、
  `orphans with an 8-byte aligned empty status slot: 87`。
- **挑宿主必须用五表口径**。少扫一张表，就会把「有人在用的行」当成无主行 —— 本轮就踩了（§3.3）。
- 「8 字节对齐」不是小事：`stride = 76`，行起点 `0x64 + i×76` 的 `%8` 在 `4 / 0` 之间交替；
  状态槽 `k` 的绝对偏移是 `row + 44 + 8k`，**只有行起点 ≡ 4 (mod 8) 时**槽 0 才落在 8 字节边界上。
  行起点 ≡ 0 的行只能退到槽 1..3，或者根本不可用。

复算（两表口径，需要三张明文在同一个目录）：

```bash
python tools/dmg_refs.py --dir <明文目录> --top 12
# 期望看到：orphan rows (no projectile/explosion reference): 187
#           orphans with an 8-byte aligned empty status slot: 87
```

五表口径的 `131 / 60` 需要把 arc / beam / status_effect 三列也并进来（方法见本节开头）。

只想改一把时，两条路：

1. 把它的弹丸行 `+60` 指向一条**真无主**行（`dmg_custom_row.py` 的做法：整行改写成你要的数值 + 借另一条无主行付哈希）；
2. 挑一条「只被它引用」的行改 —— 先按 §3.1 扫全 5 张表确认没有别的消费者。

## 5. 宿主策略

### 5.1 行内不是文件内

旧的推论是：

> `DamageInfo` 76 B / 8 成员覆盖满、零 padding ⇒ 没有可用宿主 ⇒ 伤害改不了。

**前半句对，后半句错。** 错在把「**行内**没有 8 字节空位」推成了「**整张表**没有空位」。

> **判据（背下来）**：借用别的行当宿主是允许的，但借的那 8 字节必须**既不参与主键、也不被任何读路径消费**。
> **行内无 padding ≠ 文件内无宿主。**

同一坑的另一面仓库里已有记录，形状一模一样：战备表曾借 `(NOT USED)` 行的**行首 8 字节**当宿主 ——
那 8 字节正是 `+0` 的条目 ID 与 `+4` 的名字 ID（**主键**），校正字是 64 位随机数，写进去就是把主键和名字一起改掉：
三次实机崩溃签名逐字相同 `0xc0000005 @ game.dll+0x1083a45`，会话寿命 26–29 秒
（[WORKFLOW §4.5](../cases/FILE-ROUTE-WORKFLOW-26088801.md#45-为什么校正字绝不能放进记录行) 与
[§10 坑清单](../cases/FILE-ROUTE-WORKFLOW-26088801.md#10-坑清单)；战备表重复主键的同签名崩溃见
[STRATAGEM-FIELDS](STRATAGEM-FIELDS-26088801.md) §6）。在伤害表上犯这个错更直接：行首 8 字节就是
`+0` 主键 + `+4` 标准伤害，写进去等于**同时改 ID 和伤害值**。

所以要论证的从来不是「有没有空隙」，而是「**这个 8 字节有没有人读**」—— 后者要按 §3.1 机械地扫，不能凭感觉。

### 5.2 五条候选路线

| 候选宿主 | 本表能不能用 | 依据 |
|---|---|---|
| 组头 `+16` 保留字（1 B `wide` + 7 B 保留） | **✗** | 两组头在 `0x4` / `0x3C`，`+16` 落在 `0x14` / `0x4C`，都 ≡ 4 (mod 8) |
| 行内 padding | **✗** | 8 个成员铺满 76 B（§2 的算术） |
| 数组描述符的 `pad` | **✗** | `pad` 只有 4 B（`0x60`），后 4 B 是第 0 行的 `+0` 主键 |
| **别的行的空状态槽** | **✓** | 五表口径 131 条无主行，其中 **60** 行有 8 字节对齐的空槽（§3.2） |
| **tail 追加 8 B** | **✓ 实机** | 末块结束在文件尾、明文 8 对齐 ⇒ 只需 `payload_size += 8` 再追加 8 B；G1..G6 全过（§5.3），本 build 已上机（v3） |

前三条逐条否掉，正好对应旧结论「零 padding 没有宿主」；后两条是解法。

### 5.3 tail 路线（离线门禁 + 本 build 实机）

### 5.4 挑宿主检查单

1. **扫全部带 `DamageInfoType` 的字段**（当前 5 张表，§3.1），不是只扫弹丸 + 爆炸；
2. 该行不在引用集合里（五表口径的无主行）；
3. 目标字 **8 字节对齐**：`(row + 44 + 8k) % 8 == 0`（行起点 ≡ 4 时槽 0 可用，否则退到槽 1..3）；
4. 该槽**原本为空**：`type == 0 && value == 0.0`（否则改掉了别人正在用的状态效果）；
5. 优先整行都空（131 条无主里 97 条），但**仍要过第 3 条** —— 288 就是「全空但不对齐」的反例；
6. 把选择写进报告：`host_type / record / offset / slot / value`（`dmg_edit.py` 自动落 `edit-report.json`）。

### 5.5 宿主要点名：`--host-type` 为什么是必填

- 校正字**必须**落在某个字上，工具**不替你挑**（没有默认值）⇒ 借谁的空位变成一次显式决定，而不是隐式副作用。
- 报告里落 `host_type` + `record` + `correction.offset` + `value` ⇒ 别人能复算同一份文件
  （解字是**确定性**的：同一明文 + 同一偏移 + 同一目标哈希 ⇒ 永远同一个字）。
- 工具拒绝 `host == target`；也拒绝没有对齐空槽的行（288 / 559 会被拒）。
- 门禁 G2 只允许「差异 ⊆ 目标行 ∪ 校正字」⇒ 万一借错行，门禁会露出来。
- 反过来说：如果工具自己「随手挑一个看着空的字」，就会重现 `(NOT USED)` 行首那次崩溃 —— 那正是必填的理由。

## 7. 改伤害的完整操作链

1. **取明文 + 验锚点**：`python tools/murmur64.py tables/generated_damage_settings.dl_bin` 应输出
   `D03587CCBD2FECFC`，长度 50,336 B。对不上就停（build 不对 / 解到了自己的 mod 负载 / `--key` 用错）。
2. **查共享组**：这条 id 被谁引用（弹丸 `+60`、爆炸 `+4`、arc `+36`、beam `+12`、status_effect `+44`）。
3. **选宿主**：五表口径无主 + 有空对齐槽（§5.4）；或者改用 tail（§5.3）。
4. **写值**（离线，不碰游戏）。本轮采用的是 **tail 版**（变量最少）：

   ```bash
   python tools/plain_edit.py --plain tables/generated_damage_settings.dl_bin \
       --set 0x23BC=u32:1 --out dmg-edit-out/tail.plain.dl_bin
   ```

   若坚持不改文件长度，走**行宿主版**（宿主必须先过 §5.4 的五表口径检查；537 不合格，见 §3.3）：

   ```bash
   python tools/dmg_edit.py --plain tables/generated_damage_settings.dl_bin \
       --type 116 --damage 900 --host-type <host> --out-dir dmg-edit-out
   ```

5. **读门禁输出**（下面是**行宿主版 v1**（`900` / 宿主 537）的离线复跑原样输出，用来说明 `--host-type` 的作用与门禁怎么读）：

   ```text
   plaintext generated_damage_settings.dl_bin: 50,336 B  hash D03587CCBD2FECFC
   target row   : type 116 (record 119, offset 0x23B8)
     Damage    90 -> 900
     Durable   22 -> 22  (unchanged)
   host row     : type 537 (record 530, 4 empty slots, damage 1000)
   correction   : word at 0x9DE8 (slot 0, 0 mod 8)
   after the semantic edit: hash 5DF6579A6B0C82AA (differs)
   correction word value  : 0xA1E24D24D6D297A7
   final hash             : D03587CCBD2FECFC  == original  PASS

   changed byte ranges (2):
     0x023BC..0x023BE  (2 B)  5a00 -> 8403
     0x09DE8..0x09DF0  (8 B)  0000000000000000 -> a797d2d6244de2a1
   ```

6. **封包**：`--seal --material <材料> --key <sk>` → 50,384 B；`open-key` 往返应与明文逐字节一致。
7. **部署 + 盘上回读**：备份 → 替换 → 回读（部署器 `dlbin_deploy.py` 未随仓库发布；
   最小等价物见 [WORKFLOW](../cases/FILE-ROUTE-WORKFLOW-26088801.md) §7 / §9）。
8. **实机分级验证**：一次启动只看一个可读数（[WORKFLOW](../cases/FILE-ROUTE-WORKFLOW-26088801.md) §11）。

两点说明：

- 第 5 步的 `after the semantic edit: hash 5DF6579A6B0C82AA` 是**正常中间态**：改值必然改哈希，随后由校正字拉回原值。
- 这个字是**确定性**的：v1（`900` 版）与 2026-10-22 那一轮各自独立跑，解出同一个 `0xA1E24D24D6D297A7`。
- 两条路线唯一差别是**文件长度**：行宿主 50,336 → 50,336（封包 50,384，与原版等长）；tail 50,336 → 50,344（封包 50,392）。
  想少一个变量（「宿主那个字到底有没有人读」）用 tail；想和原版等长、方便 A/B 对拍用行宿主。

### 9.2 来源二：LAS98 Heat-Driven Ramp（HD2Runtime 侧）

`refs/beam-arc/LAS98-Heat-Driven-Ramp-v2.4/` 重写伤害行时用的是**纯字节算术**：

```lua
local row = BASE_ROW:sub(1,4)          -- +0   id
         .. le(c.damage)               -- +4   标准伤害
         .. le(c.durable)              -- +8   耐久伤害
         .. le(c.ap):rep(4)            -- +12..+24  四个角度穿甲
         .. le(DEMOLITION)             -- +28  拆解力
         .. BASE_ROW:sub(33)           -- +32 起原样保留
```

`sub(33)` 是 1-based，对应字节偏移 **32** ⇒ 它明确把 `+32` 之后原样保留。这条**独立**印证了
`+4` / `+8` / `+12..+24` / `+28` 四个位置，与 §9.1 完全吻合。

### 9.5 顺带定名：块 0 `DamageArmorAngles`

filediver 的结构体给出：

```go
type DamageArmorAngles struct {
    Projectile [4]float32
    DPS        [4]float32
}
```

本 build 块 0 实测正好 8 个 f32 = `25, 60, 80, 90, 25, 60, 80, 90` ⇒
**`Projectile[4] = 25/60/80/90`、`DPS[4] = 25/60/80/90`**（两组当前同值）。

⚠ 语义仍未定：这四个角度很可能对应 `+12..+24` 那四档穿甲的**入射角分界**（直射 / 稍偏 / 大偏 / 极端），
但**没有做改动实验**，「四格 ↔ 四角度」的对应关系仍是 ⚠（§8.4）。
