# 虚拟机路线：宿主读 guest 内存（build 25988413 时代）

> 目的：绕开 EAC 的句柄剥离，拿 HD2 全量内存。
> 现状：**能力已证实，目标被 EAC 的虚拟机检测挡住**。本文件记录证据、已试过的伪装、以及还剩什么。

## 1. 已证实的部分（✓ 实测）

### 1.1 宿主能读 guest 内存

挂起 VM → `.vmem`（16.00 GiB）→ 直接在宿主机上做字节搜索：

| 针 | 命中 |
|---|---|
| `DESKTOP-7HB8741`（guest 主机名） | 591 ASCII + 2,604 UTF-16 |
| `192.168.150.131`（guest IP） | 20 ASCII + 491 UTF-16 |

16 GiB 全盘扫描 ≈ 100 秒。**EAC 的 `ObRegisterCallbacks` 在这条链路上不存在** —— 读的是磁盘文件。

### 1.2 `.vmem` 是线性物理内存镜像，但**文件偏移 ≠ 物理地址**

vmss2core 自报的内存区间：

```
region[0]  0x000000000 – 0x0C0000000   (3 GiB)
region[1]  0x100000000 – 0x440000000   (13 GiB)
合计 16 GiB = .vmem 文件大小
```

⇒ 第二段换算：`PA = 0x100000000 + (off - 0xC0000000)`。写分析器必须带这个映射。

### 1.3 `vmss2core -W8` 对 Win11 guest 不可用

```
Error parsing Windows data.
Cannot translate linear address fffff78000000000.
Cannot create memory.dmp
```

与 [KB 323788](https://knowledge.broadcom.com/external/article/323788/) 记录的现象一致（guest 带 VBS/虚拟化特性时出不了标准 dump）。
**但这不影响我们**：`.vmem` 明文可直读，不需要它的格式。

## 2. 被挡住的部分：EAC 拒绝在虚拟机里启动

### 2.1 现象

游戏弹「启动错误 / 无法在虚拟机下运行」，后台是 Easy Anti-Cheat 的 logo。

### 2.2 内存里挖到的原文（决定性）

挂起后从 `.vmem` 扫 UTF-8 中文串，命中处上下文：

```
[EAC Bootstrapper] [Info] Loader initializing with bootstrapper version 1.9.4, architecture: x86-64.
[EAC Bootstrapper] [Info] Connecting to https://modules-cdn.eac-prod.on.epicgames.com/modules/...
[EAC Bootstrapper] [Info] Connect result: No error (0) Response Code: 200
[EAC Bootstrapper] [Info] Launcher finished with: 206, '无法在虚拟机下运行'
[EAC Bootstrapper] [Info] Terminating with: 206
[EAC Bootstrapper] [Info] Downloaded 33527224 bytes in 3437 ms
```

⇒ **拒绝点是 EAC 启动器（bootstrapper 1.9.4）**，早于游戏进程、早于它的内核驱动；模块下载是成功的。
⇒ 那句中文是 EAC 自己的 zh_cn 本地化文案，不是游戏的。

### 2.3 旁边还躺着 EAC 的错误键字典

```
error_system_configuration  error_system_version  error_tool_forbidden
error_module_forbidden      error_file_forbidden  error_no_settings_file
```

## 3. 已试过的伪装（全部失败）

写进 `.vmx` 的项：

```
hypervisor.cpuid.v0           = FALSE   # 抹 CPUID 厂商串 VMwareVMware
monitor_control.restrict_backdoor = TRUE # 封 VMware 背板 I/O 端口
cpuid.1.ecx                   = "0---:----:----:----:----:----:----:----"  # bit31 置 0
smbios.reflectHost = board-id.reflectHost = serialNumber.reflectHost = TRUE
hw.model.reflectHost = manufacturer.reflectHost = productName.reflectHost = TRUE
ethernet0.addressType = static / address = 02:50:F3:1A:2B:3C   # 去掉 00:0C:29
isolation.tools.{get,set}{PtrLocation,Version}.disable = TRUE
```

结果：**仍然 206**。

### 3.1 失败的关键怀疑点（⚠ 推断，未证实）

宿主开着 Hyper-V/VBS（`HypervisorPresent = True`），VMware 因此跑在 **WHP/ULM 兼容模式**（`vmware.log` 里有 `Syncing WHP TSCs`）。
**在 ULM 模式下，CPU 的 "hypervisor present" 位由宿主 hypervisor 设置，VMware 未必能改** —— 所以 `cpuid.1.ecx` 掩码可能根本没生效。

内存里同时存在这两条线索（但可能是上次开机的残留页，不能定论）：

```
HOSTINFO: CPUID hypervisor bit is set, but no hypervisor vendor signature is present.
Microsoft Hv
```

**"有 hypervisor、但厂商串被抹掉"这个组合本身就是最可疑的指纹。**

### 3.2 还躲不掉的 VMware 痕迹（`.vmx` 改不了）

| 痕迹 | 在哪 |
|---|---|
| 固件 ROM 里的 `VMware` / `EFI VESA SVGA` | 物理地址 0xC0000 附近 |
| VMware Tools 的字符串与驱动 | guest 里装着 Tools |
| PCI 设备 `VEN_15AD` | SVGA / VMCI / NVMe 控制器 |
| ACPI OEM 表 | SMBIOS 反射改不了 ACPI OEM ID |

## 4. 下一步（未做）

1. **让 guest 自己报 CPUID 状态**（一条 `systeminfo`，看有没有"已检测到虚拟机监控程序"）—— 一条命令就能判定掩码是否生效。
2. 若掩码无效：**宿主关 Hyper-V/VBS 后重启**（`bcdedit /set hypervisorlaunchtype off` + 关内存完整性），让 VMware 走原生模式。代价：WSL2/容器停止、DSH 会话中断一次。
3. 若关掉后仍被拦：说明 EAC 查的是固件/PCI 这类 `.vmx` 改不了的痕迹，VM 路线应当收摊。

## 5. 本轮产出的工具（`D:\mod\vm-dump\`）

| 工具 | 作用 |
|---|---|
| `analyze_dump.py` | 认格式（PAGE/MDMP/VMEM）、算熵判加密、按 ASCII/UTF-16 搜针 |

## 6. 结论（2026-10-21 14:15）：VM 路线关闭

CPUID 侧已经**干净**了（这是决定性对照组）：

```
(Get-CimInstance Win32_ComputerSystem).HypervisorPresent  ->  False
systeminfo -> "Hyper-V 要求: 虚拟机监视器模式扩展: 否"
```

也就是说 guest 自己都不认为有 hypervisor。**但 EAC 仍然返回 206**。所以它的判定不在 CPUID。

### 6.1 guest 里的实测指纹（三条命令的原始输出）

| 检查项 | 实测值 | 可伪装? |
|---|---|---|
| 系统厂商 / 型号 | `Micro-Star International Co., Ltd.` / `Katana 15 B13VFK` | ✓ reflectHost 生效 |
| 主板厂商 | `Intel Corporation` | ✓ 生效 |
| **主板型号** | **`440BX Desktop Reference Platform`** | ✗ VMware 虚拟芯片组 |
| **BIOS 厂商** | **`VMware, Inc.`** | ✗ reflectHost 不覆盖此字段 |
| **BIOS 版本** | **`VMW201.00V.21805430.B64.2305221830`** | ✗ |
| **显示适配器** | **`VMware SVGA 3D` / 9.17.6.5** | ✗ |
| **磁盘** | **`VMware Virtual NVMe Disk`** | ✗ |
| **PCI 设备** | **约 30 个 `VEN_15AD`**：SVGA(0405) · VMCI(0774) · USB3(07E0) · HD Audio(1975) · 根端口(07A0) | ✗ |
| 服务 | `VMTools` / `VGAuthService` / `vm3dservice` 运行中 | ~ 可卸 |

### 6.2 判定

**这些是 VMware 虚拟硬件的身份，不是配置项。** `.vmx` 能改的是 CPUID 掩码、DMI 部分字段、MAC、背板端口；
改不了 BIOS 厂商串、芯片组型号、虚拟显卡/磁盘型号、PCI 厂商 ID。

⇒ 要让 EAC 认不出虚拟机，必须换成可完全自定义 SMBIOS/ACPI/PCI ID 的 hypervisor（QEMU/KVM 一类），
在当前的 Windows 宿主上不现实。**VM 路线就此关闭，不再投入。**

### 6.3 这条路仍然有价值的副产品

1. **"宿主读 guest 内存"这一能力被完整证实**（§1），工具三件套留在 `D:\mod\vm-dump\`；
2. **一套可复现的 EAC 取证手法**：挂起 → `.vmem` → 扫字符串，能直接读出 EAC 启动器自己的日志与错误码
   （§2.2 的 `Launcher finished with: 206` 就是这么拿到的）—— 这套手法对别的带反作弊程序同样适用；
3. 证明了 **`.vmx` 级伪装打不过新一代反作弊**，这个负面结论以后不必重试。
