# 更新后差异：25988413 → 26088801（7.2.1 hotfix）

官方说明只有一条：**修"另一名玩家加入/离开小队时崩溃"**。下面是逐层实测的差异，
全部只读、离线（解封 `data/game` 里的密封盒，不启动游戏、不碰进程内存）。

一句话结论：**密钥没变、类型库逐字节没变、55 张表一张都没变；变的是可执行代码和 bundle 打包。**
唯一一张和我们 09:52 缓存对不上的表（`passive_bonuses`）在 18:49 的全表字典里就已经是新值了，
所以它的改动早于这次写盘。

---

## 1. 密钥与封装层（✓ 实测）

```
55 张 generated_*.dl_bin + dl_library.dl_typelib   全部解封成功，0 失败
```

解封用的是同一个 `recipient.sk`。这条最重要：只要它还能解，我们的全部表工具链就不用改。

## 2. 类型库（✓ 逐字节相同）

```
旧明文 1,080,024 B   新明文 1,080,024 B   差异字节 0   差异段 0
类型 1208 / 成员 7349 / 枚举 345           全部相同
零个类型的 size32/size64 发生变化
```

顺带纠正一个易错点：磁盘上的 sealing 是 `明文 + 48 B`（32 B 临时公钥 + 16 B tag），
所以 `文件大小` 和 `明文大小` 差 48。上一轮差点把"文件大了 48 B"当成"类型库改了"。

## 3. 表（✓ 55 张都没变）

基线用 `refs/table-geometry.json`（build 25988413，2026-10-22 18:49 生成）：

```
identical                     21   明文逐字节相同（这 21 张我们有旧明文）
structure-same                33   明文字节数 + 组数相同（没有旧明文，只能证到结构）
structure-same-cache-differs   1   结构同，但与我们 09:52 的明文缓存不同（见 §4）
changed                        0
```

也就是说：**表结构、行数、步长全都没动**，21 张能比哈希的表也逐字节相同。

## 4. 唯一有内容变化的那张表：`customization_passive_bonuses`

它才是这轮"真的改了什么"的答案，但**不是这次写盘造成的**：

```
2026-10-22 09:52  我们 dump 的明文（本仓库 refs/dlbin/plaintext-all）     4992 B
2026-10-22 18:49  全表字典记录的明文（同一台机器、更新前）                4016 B
2026-10-22 20:56  更新写盘后实测                                          4016 B
```

18:49 就已经是 4016，所以这张表的改动发生在 09:52 与 18:49 之间（今天更早的一次更新），
今晚这次 20:56 的写盘没再动它。

**改的是什么**：记录结构本身没变，变的是记录后面那个 16 字节条目数组的长度。

```
组布局 = [56 B 记录] + [条目数 × 16 B 条目]        payload 恰好等于两者之和
记录字段：
  +0   u32   序号（1, 6, 8 …）
  +4   u32   名字的本地化 ID（"EXTRA PADDING" 等）
  +8   u32   ID（未定性）
  +12  u32   ID（未定性）
  +16  u32   56            ← 记录长度，自描述
  +20  u32   0
  +24  u32   条目数        ← 这次变的就是它（3→1, 4→2, 5→3 …）
  +28  u32   0
  +32  u64   0xFFFFFFFFFFFFFFFF
  +40  u32   0
  +48  u32   0
条目（16 B）：u32 属性 id | u32 种类(1/2/3) | f32 值 | u32 附加 id
```

**被删掉的是每个被动数组末尾的两条**，而且两条在所有 33 个被动里都一模一样：

```
id 0x2875f44a  种类 1  值 2.0  附加 0     出现 25 次
id 0x93eb16a7  种类 3  值 2.0  附加 0     出现 24 次
```

被保留的条目的"附加 id"字段都是非零值，这两条是 0 —— 看起来像"占位/默认"条目被清掉，
而不是数值平衡调整（值恒为 2.0、附加字段恒为 0）。⚠ 这两个 id 对应什么属性没定位，
所以"删了会不会影响手感"没有结论，只能说：结构上确定删的是这两条。

`+24` 语义这次也顺手定了：它就是**条目数**（`payload = 56 + 条目数×16` 在 33 个组上全部成立）。

## 7. 复跑

```bash
python tools/build_diff.py            --sk <sk>     # 文件层 + 封装层 + 结构层，逐表"变了没"
python tools/build_geometry_diff.py   --sk <sk>     # 用旧 build 的字典几何对照 55 张表
python tools/build_cache.py           --sk <sk>     # 把当前 build 的明文按 buildid 另存一份
```

`build_cache.py` 是这轮的教训产物：之前只有一份 `plaintext-all/`，
游戏更新后它就悄悄变成"上一个 build 的副本"，再拿它当基线就会得出错误的"改了什么"。
现在每个 build 一份 `refs/dlbin/plaintext-<buildid>/`，diff 永远有干净基线。

## 8. 三态小结

**✓ 实测**：密钥没变（56/56 解封成功）；类型库明文 0 差异；55 张表结构全同、21 张明文全同；
exe/game.dll 哈希变、大小不变；bundles.nxa +151 B、5 个 bundle ±64 KB、25 个不变；
战备名字重跑结果与已发布文件逐字节相同。

**✗ 否证**：`passive_bonuses` 的改动不是这次 20:56 写盘造成的（18:49 的字典已是新值）；
`+24` 不是"记录长度"（是条目数，记录长度在 `+16`）。

**⚠ 未定**：被删的两个条目 id（`0x2875f44a` 种类 1、`0x93eb16a7` 种类 3，均 ×2.0）
对应什么属性；33 张没有旧明文的表只能证明结构没变、不能排除"同尺寸下的数值改动"；
已装 Lua patch 在新版是否需要调整。
