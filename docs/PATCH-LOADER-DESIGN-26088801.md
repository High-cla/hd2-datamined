# 数据文件路线的"加载器"：不需要执行权，只需要一个离线合成器

## 1. 旧加载器那套发现方法，确实不能用了

Bingus Shared Loader 的两件本事是绑在一起的：

* **执行权**：覆盖 `boot` 资源（id `murmur64("boot")` = `0xF476DF93691895FA`，活在包
  `9ba626afa44a3aa3` 里），让引擎自己加载它那段 LuaJIT 脚本 —— 这是唯一一个引擎会主动加载的 lua。
* **发现 mod**：拿到执行权之后，用 `ffi` 调 `kernel32` 去枚举 `data/*.patch_N`，再把找到的 mod
  逐个挂进运行时。

build 25988413 之后 `ffi` 没了，第二件本事直接断；第一件虽然还能做（boot 覆盖实测有效），
但跑起来的 Lua 已经**看不见文件系统、也改不了内存** —— 所以旧那套"枚举 + 注入"没了立足点。

## 2. 但我们的路线（改数据文件）根本不需要它

`patch_N` 是**引擎自己读的**：把 `data/<包名>.patch_N` 放在那里，引擎启动时按序号合并进对应包。
不需要执行任何代码，也不需要枚举 —— 引擎替我们做了。所以这条路线缺的不是加载器，是**共存**。

社区说"数据 mod 不能共存"，拆开是两条机制，两条都有实测依据：

| 机制 | 说明 | 依据 |
|---|---|---|
| **文件名撞车** | 每个 mod 都按 `9ba626afa44a3aa3.patch_0` 发布，后装的直接盖掉先装的 | 所有社区数据 mod 的包名/槽位都是同一个 |
| **序号必须连续** | 引擎按 `patch_0..patch_N` **连续**合并；中间缺号，**后面的一律不生效**（磁盘上文件在、md5 对，也当没看见） | `docs/LOADER-SPEC-25988413.md`：把 patch_1/2 删掉只留 patch_3，探针 0/0/6 全 absent；连续时 3/3/3 |

第二条尤其阴：很多安装器"删除/重排补丁"时会在序列里留个洞，用户看到的现象就是
"两个 mod 一起装，有一个消失了"。**这跟 mod 内容无关，纯粹是槽位管理问题。**

## 3. 解法：离线合成器（`tools/patch_compose.py`）

在这条路线上，"加载器"应该做的事是：

```
scan     列出某个 data 目录里每个包的槽位与空洞（查"为什么不生效"）
merge    读多个补丁的条目 -> 按资源 id 求并集 -> 冲突检测 -> 合成一个补丁 + 回读验证
install  把合成结果放到该包的下一个连续槽位（拒绝在有空洞的链上安装）
```

判据（全部离线）：

* 同 id 同内容 → 去重；同 id **不同内容** → 冲突，默认拒绝合成（同一资源两个 mod 各写一份，
  语义上必须人工选边，`--prefer` 指定）；
* 合成后逐条回读，`toc` 与 `gpu_resources` 附流都要与来源逐字节一致；
* 安装前检查目标包槽位连续，只在**下一个连续槽位**写入。

### 实测（离线，用我们自己装着的两个补丁）

```
$ python tools/patch_compose.py scan --data "<game>/data"
9ba626afa44a3aa3: 槽位 [0, 1, 2, 3, 4]  空洞 无
  patch_0: 1 条 /  23,120 B  lua×1
  patch_1: 1 条 /  15,888 B  lua×1
  patch_2: 1 条 /   5,664 B  lua×1
  patch_3: 6 条 /   6,608 B  bones×1 material×1 texture×4
  patch_4: 1 条 / 418,432 B  lua×1

$ python tools/patch_compose.py merge --mods ...patch_3 ...patch_4 --out out/merged
并集 7 条；同内容去重 0 条；冲突 0 条
合成 out/merged/9ba626afa44a3aa3.patch_0  toc=421,232 B  gpu=2,272,056 B
  PASS 回读条目集合一致（7 条）
  PASS 逐条 toc 字节一致
  PASS gpu 附流一致
```

也就是说：**7 条异种资源（骨骼/材质/贴图/lua）能被合进一个补丁，内容不变** —— 这就是"共存"的
最低要求，而且全程离线可复跑。

## 4. ⚠ 还没定的四件事（都影响能不能真装）

1. **容器头的 28 字节**：`resource_patch.py repack` 重建 `patch_3` 时，偏移 16 起的 28 字节
   我们写成 0，而原文件里有值（`ce09f5f4…` / `4b91a040…` / `0024e400…`），总长度也差 48 B。
   条目级完全一致，但**容器级不等于原文件**。这 28 字节是什么（构建工具指纹？依赖清单？）没查，
   要确认引擎对它们不敏感，得做一次对照实验。
2. **同 id 冲突时引擎谁赢**：是"后号覆盖前号"还是"先号优先"没测过。所以合成器默认拒绝冲突，
   不赌顺序。
3. **单补丁上限**：条目数 / 字节数有没有上限未知（现在最大的是 418 KB / 6 条）。
4. **多包**：`patch_N` 的连续性是**按包**算的。如果一个 mod 想改另一个包，就得各自一条链；
   跨包的合并策略还没设计。

## 5. 下一步（按代价排序）

1. 用合成器做一次**真装**：把两个小 mod 合成一个补丁装到下一个空槽，进游戏确认两个效果都在
   （这一步要启动游戏，等确认）。
2. 顺手把 §4.1 的 28 字节搞清：对比一个用 `srkit mod` 构建的补丁和一个社区补丁的头部，
   看哪些字段非零、是否与构建工具有关。
3. §4.2 的覆盖顺序：设计一个两行改同一资源的对照实验（两个补丁分别把同一字段改成不同值），
   进游戏看谁生效 —— 这条决定了合成器的冲突策略要不要支持"分层覆盖"。
